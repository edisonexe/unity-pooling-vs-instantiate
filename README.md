# Unity Object Pooling Benchmark (Stress-Test Simulation)

![Unity Version](https://img.shields.io/badge/Unity-6_LTS_(6.3)-blue?logo=unity)
![Architecture](https://img.shields.io/badge/Architecture-SOLID_%2F_DIP_%2F_MVP-orange?style=flat-square)
![DI Framework](https://img.shields.io/badge/DI%20Framework-Zenject-green)

Высокопроизводительный бенчмарк для демонстрации и сравнения эффективности кастомного паттерна **Object Pool** против классического (наивного) подхода **Instantiate / Destroy** в среде Unity под экстремальной рантайм-нагрузкой (3000+ активных объектов одновременно).

## Архитектура и Структура проекта

Проект спроектирован по принципам **SOLID / DIP** с полным отказом от хаотичных синглтонов. Сборка графа объектов, управление их жизненным циклом и проброс зависимостей осуществляются через IoC-контейнер **Zenject** (Composition Root).

Кодовая база строго разделена на независимые слои:
* **Domain:** Чистые C# данные, конфигурации (ScriptableObject) и реестры сущностей.
* **Infrastructure:** Обобщенная утилитарная логика пулинга и системных контейнеров сцены.
* **Gameplay Services:** Пассивные службы и фабрики (оркестраторы вычислений).
* **Gameplay Systems:** Активные обновляемые сущности, реализующие интерфейс `ITickable` вместо стандартного Update.
* **UI (MVP):** Полное разделение логики интерфейса и представления для обеспечения реактивного обновления данных.

### 📂 Иерархия сцены
Для минимизации оверхеда на отрисовку интерфейса редактора Unity (Hierarchy Window) во время спавна десятков тысяч объектов, иерархия сцены была строго категоризирована. Динамические сущности изолированы внутри независимых холдеров в группе `[DYNAMIC]`:

```text
▼ [DI]
    SceneContext            # Точка входа DI-контейнера
▼ [SYSTEMS]
    Pool Service            # Логика пулов (Prewarm и очереди)
    Plane Spawn Points Cache
▼ [DYNAMIC]
  ▼ Simulation Containers   # Инфраструктурный провайдер холдеров
      Projectiles Holder    # Контейнер для спавна снарядов
      Targets Holder        # Контейнер для спавна целей
```

## Результаты и итоги бенчмарка
Наивный подход с регулярным вызовом `Instantiate` и `Destroy` создавал непрерывный поток тяжелых рантайм-аллокаций памяти под тысячи генерируемых объектов каждый кадр. В рантайме это приводило к регулярным микрофризам в моменты автоматической сборки мусора, из-за чего средний FPS падал, а график времени кадра становился нестабильным.

Переход на паттерн `Object Pool` полностью ликвидировал аллокации от пересоздания сущностей, остались лишь незначительные внутренние подкапотные аллокации самого физического движка Unity (Physics), которые мы не рассматриваем в данном бенчмарке. За счет полного устранения оверхеда на выделение памяти и исключения фризов от Garbage Collector время кадра стабилизировалось, что **обеспечило прирост среднего FPS примерно на 30%** в условиях экстремального теста. Симуляция при пиковой нагрузке **стала работать предсказуемо, стабильно и плавно**.
